== 개요 (Introduction)

지금까지는 정점별 색상(per-vertex colors)을 사용해 도형에 색을 입혔지만, 이는 표현에 한계가 많은 방식입니다. 이번 장에서는 도형을 더욱 흥미롭고 실감 나게 꾸밀 수 있도록 텍스처 매핑(texture mapping)을 구현해 보겠습니다. 이를 바탕으로 향후 장에서는 기본적인 3D 모델을 불러와 화면에 그리는 작업도 진행할 예정입니다.

애플리케이션에 텍스처를 추가하려면 다음과 같은 단계가 필요합니다.

* 디바이스 메모리가 할당된 이미지 객체 생성
* 이미지 파일의 픽셀 데이터로 이미지 객체 채우기
* 이미지 샘플러(sampler) 생성
* 결합된 이미지 샘플러 디스크립터(combined image sampler descriptor)를 추가하여 텍스처에서 색상 추출하기

이전에도 이미지 객체를 다룬 적이 있지만, 당시에는 스왑 체인 확장 기능에 의해 자동으로 생성된 것이었습니다. 이번에는 우리가 직접 이미지 객체를 만들어야 합니다. 이미지를 생성하고 데이터를 채우는 과정은 정점 버퍼(vertex buffer)를 만들 때와 비슷합니다. 먼저 임시 저장 공간인 스테이징 리소스(staging resource)를 만들어 픽셀 데이터를 채운 뒤, 이를 렌더링에 사용할 최종 이미지 객체로 복사하는 방식을 사용합니다. 이 과정에서 스테이징 전용 이미지를 만드는 것도 가능하지만, {vk}에서는 {VkBuffer}[``VkBuffer``]에서 이미지로 픽셀을 직접 복사할 수도 있습니다. 실제로 일부 하드웨어에서는 이 API가 더 빠르게 작동합니다. 따라서 우리는 먼저 이 버퍼를 생성해 픽셀 값을 채운 다음, 픽셀을 복사해 넣을 이미지 객체를 만들 것입니다. 이미지를 만드는 과정은 버퍼 생성과 크게 다르지 않습니다. 이전에 보셨던 것처럼 메모리 요구 사양을 조회하고, 디바이스 메모리를 할당한 뒤 이를 바인딩하는 단계를 거치게 됩니다.

하지만 이미지를 다룰 때는 특별히 신경 써야 할 추가 요소가 있습니다. 바로 이미지 레이아웃(layout)입니다. 레이아웃은 메모리에 픽셀이 배치되는 구조를 결정합니다. 그래픽 하드웨어의 작동 방식 특성상, 단순히 픽셀을 가로 한 줄씩 차례대로 저장하는 것은 성능 면에서 최선이 아닐 수 있습니다. 따라서 이미지로 어떤 작업을 수행할 때는 해당 작업에 가장 최적화된 레이아웃으로 변경해 주어야 합니다. 사실 우리는 이미 렌더 패스(render pass)를 설정할 때 다음과 같은 레이아웃들을 접한 적이 있습니다.

[cols="5a,5",options=header]
|===
|플래그
|설명

|``VK_IMAGE_LAYOUT_PRESENT_SRC_KHR``
|화면 표시(presentation)에 최적화된 상태

|``VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL``
|프래그먼트 셰이더의 색상 출력 대상(attachment)에 최적화된 상태

|``VK_IMAGE_LAYOUT_TRANSFER_SRC_OPTIMAL``
|{vkCmdCopyImageToBuffer}[``vkCmdCopyImageToBuffer``]처럼 복사 작업의 소스(원본)로 쓰기에 최적화된 상태

|``VK_IMAGE_LAYOUT_TRANSFER_DST_OPTIMAL``
|{vkCmdCopyBufferToImage}[``vkCmdCopyBufferToImage``]처럼 복사 작업의 데스티네이션(대상)으로 쓰기에 최적화된 상태

|``VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL``
|셰이더에서 텍스처 데이터를 읽어와 샘플링하기에 최적화된 상태
|===

이미지의 레이아웃을 전환하는 가장 대표적인 방법 중 하나는 파이프라인 장벽(pipeline barrier)을 사용하는 것입니다. 파이프라인 장벽은 본래 이미지가 읽히기 전에 쓰기 작업이 먼저 완료되도록 보장하는 등 리소스 접근 동기화를 위해 주로 쓰이지만, 레이아웃 전환 용도로도 사용할 수 있습니다. 이번 장에서는 파이프라인 장벽을 활용해 레이아웃을 바꾸는 방법을 알아보겠습니다. 참고로 장벽은 ``VK_SHARING_MODE_EXCLUSIVE`` 설정을 사용할 때 큐 패밀리(queue family) 간의 소유권을 이전하는 목적으로도 사용됩니다.

== 이미지 불러오기 (Loading an image)

다음과 같이 이미지 라이브러리를 포함(include)합니다.

[source,cpp]
----
#define STB_IMAGE_IMPLEMENTATION
#include <stb_image.h>
----

해당 헤더 파일은 기본적으로 함수의 프로토타입(선언부)만 정의합니다. 따라서 소스 파일 중 딱 한 곳에는 헤더를 포함하기 전에 반드시 ``STB_IMAGE_IMPLEMENTATION``을 먼저 정의해야 함수의 본문(구현부)이 함께 포함됩니다. 이 과정을 누락하면 링크 에러(linking errors)가 발생하게 됩니다.

[source,cpp]
----
void initVulkan() {
    ...
    createCommandPool();
    createTextureImage();
    createVertexBuffer();
    ...
}
...
void createTextureImage() {

}
----

이미지를 불러와 Vulkan 이미지 객체에 업로드할 새로운 함수인 ``createTextureImage``를 생성합니다. 이 함수 내에서는 커맨드 버퍼를 사용할 예정이므로, 반드시 ``createCommandPool``을 호출한 이후에 실행되도록 위치시켜야 합니다.

텍스처 이미지들을 저장할 수 있도록 ``shaders`` 디렉토리와 같은 위치에 ``textures``라는 새 디렉토리를 만듭니다. 우리는 이 디렉토리에 있는 ``texture.jpg``라는 이미지를 불러올 것입니다. 샘플로는 512 x 512 픽셀로 크기를 조정한 link:https://pixabay.com/en/statue-sculpture-fig-historically-1275469/[CC0 라이선스 이미지]를 선택했지만, 원하신다면 어떤 이미지든 자유롭게 고르셔도 됩니다. 이 라이브러리는 JPEG, PNG, BMP, GIF 등 가장 흔히 쓰이는 이미지 파일 포맷들을 대부분 지원합니다.

image::../assets/texture.jpg[align=center, width=50%]

이 라이브러리를 사용하면 매우 간단하게 이미지를 불러올 수 있습니다.

[source,cpp]
----
void createTextureImage() {
    int texWidth, texHeight, texChannels;
    stbi_uc* pixels = stbi_load("./textures/texture.jpg", &texWidth, &texHeight, &texChannels, STBI_rgb_alpha);
    VkDeviceSize imageSize = texWidth * texHeight * 4;

    if (!pixels) {
        throw std::runtime_error("failed to load texture image!");
    }
}
----

``stbi_load`` 함수는 파일 경로와 불러올 채널 수를 인자로 받습니다. 여기서 ``STBI_rgb_alpha`` 값을 지정하면 이미지에 알파 채널이 없더라도 강제로 알파 채널을 포함하여 불러오게 됩니다. 이는 향후 다른 텍스처들과 형식을 통일하여 관리하기에 유용합니다. 가운데 3개의 매개변수는 출력용 인자로, 이미지의 가로 크기(너비), 세로 크기(높이), 그리고 실제 원본 이미지의 채널 수가 각각 저장됩니다. 함수가 반환하는 포인터는 픽셀 값 배열의 첫 번째 요소를 가리킵니다. ``STBI_rgb_alpha``를 사용한 경우, 픽셀은 가로 줄 단위(row by row)로 배열되며 픽셀당 4바이트를 차지합니다. 따라서 전체 배열은 총 ``texWidth * texHeight * 4``개의 값을 가집니다.

== 스테이징 버퍼 (Staging buffer)

이제 {vkMapMemory}[``vkMapMemory``]를 사용해 픽셀 데이터를 복사할 수 있도록, 호스트 가시적 메모리(host visible memory)에 버퍼를 생성해 보겠습니다. ``createTextureImage`` 함수에 이 임시 버퍼를 다룰 변수들을 추가합니다.

[source,cpp]
----
// void createTextureImage()
VkBuffer stagingBuffer;
VkDeviceMemory stagingBufferMemory;
----

이 버퍼는 매핑이 가능해야 하므로 호스트 가시적 메모리에 배치해야 하며, 나중에 이미지로 데이터를 복사할 수 있도록 전송 소스(transfer source)로 사용할 수 있어야 합니다.

[source,cpp]
----
// void createTextureImage()
createBuffer(imageSize, VK_BUFFER_USAGE_TRANSFER_SRC_BIT,
            VK_MEMORY_PROPERTY_HOST_VISIBLE_BIT | VK_MEMORY_PROPERTY_HOST_COHERENT_BIT, stagingBuffer,
            stagingBufferMemory);
----

버퍼 생성을 마쳤다면, 이미지 로딩 라이브러리를 통해 얻은 픽셀 값들을 버퍼로 곧바로 복사할 수 있습니다.

[source,cpp]
----
// void createTextureImage()
void* data;
vkMapMemory(_device, stagingBufferMemory, 0, imageSize, 0, &data);
memcpy(data, pixels, static_cast<size_t>(imageSize));
vkUnmapMemory(_device, stagingBufferMemory);
----

복사가 끝난 후에는 원본 픽셀 배열을 정리(free)하는 것을 잊지 마세요.

[source,cpp]
----
// void createTextureImage()
stbi_image_free(pixels);
----

== 텍스처 이미지 (Texture image)

셰이더가 버퍼에 있는 픽셀 값에 직접 접근하도록 설정할 수도 있지만, Vulkan에서는 이 목적으로 이미지 객체를 사용하는 것이 훨씬 좋습니다. 이미지 객체를 사용하면 2D 좌표를 활용할 수 있어 색상을 더 쉽고 빠르게 추출할 수 있기 때문입니다. 이미지 객체 내부의 픽셀은 텍셀(texel)이라고 부르며, 이제부터는 이 용어를 사용하겠습니다. 다음과 같이 새로운 클래스 멤버 변수들을 추가해 줍니다.

[source,cpp]
----
// HelloTriangleApplication
VkImage _textureImage;
VkDeviceMemory _textureImageMemory;
----

이미지에 필요한 매개변수들은 {VkImageCreateInfo}[``VkImageCreateInfo``] 구조체에 지정합니다.

NOTE: ``VkExtent3D``는 작성자가 추가함

[source,cpp]
----
// void createTextureImage()
VkExtent3D imageExtent{
    .width = static_cast<uint32_t>(texWidth),
    .height = static_cast<uint32_t>(texHeight),
    .depth = 1,
};
VkImageCreateInfo imageInfo{
    .sType = VK_STRUCTURE_TYPE_IMAGE_CREATE_INFO,
    .imageType = VK_IMAGE_TYPE_2D,
    .extent = imageExtent,
    .mipLevels = 1,
    .arrayLayers = 1,
};
----

``imageType`` 필드에 지정하는 이미지 유형은 이미지 안의 텍셀들을 어떤 좌표계로 참조할지 {vk}에 알려주는 역할을 합니다. 이미지에는 1D, 2D, 3D 유형이 있습니다. 1차원(1D) 이미지는 데이터 배열이나 그라데이션을 저장할 때 쓰이고, 2차원(2D) 이미지는 주로 텍스처에 쓰이며, 3차원(3D) 이미지는 복셀(voxel) 볼륨 등을 저장할 때 사용할 수 있습니다. ``extent`` 필드는 이미지의 크기, 즉 각 축에 텍셀이 몇 개씩 배치되는지를 지정합니다. 그렇기 때문에 깊이(``depth``) 값은 ``0``이 아니라 반드시 ``1``이어야 합니다. 우리가 사용할 텍스처는 배열 형식이 아니며, 당장은 밉맵(mipmapping)도 사용하지 않을 것입니다.

[source,cpp]
----
// void createTextureImage()
imageInfo.format = VK_FORMAT_R8G8B8A8_SRGB;
----

{vk}은 매우 다양한 이미지 포맷을 지원하지만, 여기서는 버퍼에 있는 픽셀과 동일한 포맷을 텍셀에 지정해야 합니다. 그렇지 않으면 복사 작업(copy operation)이 실패하게 됩니다.

[source,cpp]
----
// void createTextureImage()
imageInfo.tiling = VK_IMAGE_TILING_OPTIMAL;
----

``tiling`` 필드는 다음 두 가지 값 중 하나를 가질 수 있습니다.

* ``VK_IMAGE_TILING_LINEAR``: 앞서 다룬 픽셀 배열처럼 텍셀이 행 우선(row-major) 순서로 배치됩니다.
* ``VK_IMAGE_TILING_OPTIMAL``: 최적의 접근 성능을 내도록 구현(하드웨어)이 정의한 순서로 텍셀이 배치됩니다.

이미지 레이아웃과 달리, 타일링 모드는 한 번 설정하면 나중에 변경할 수 없습니다. 이미지 메모리에 직접 접근해 텍셀을 다루고 싶다면 ``VK_IMAGE_TILING_LINEAR``를 사용해야 합니다. 하지만 우리는 스테이징 이미지 대신 스테이징 버퍼를 사용할 것이므로 이 모드가 필요하지 않습니다. 따라서 셰이더에서 가장 효율적으로 접근할 수 있도록 ``VK_IMAGE_TILING_OPTIMAL``을 사용할 것입니다.

[source,cpp]
----
// void createTextureImage()
imageInfo.initialLayout = VK_IMAGE_LAYOUT_UNDEFINED;
----

이미지의 초기 레이아웃을 뜻하는 ``initialLayout``에 지정할 수 있는 값은 다음 두 가지뿐입니다.

* ``VK_IMAGE_LAYOUT_UNDEFINED``: GPU가 사용할 수 없는 상태이며, 첫 번째 레이아웃 전환 시 기존 텍셀 데이터가 파기됩니다.
* ``VK_IMAGE_LAYOUT_PREINITIALIZED``: GPU가 사용할 수 없는 상태이지만, 첫 번째 레이아웃 전환 시에도 텍셀 데이터가 유지됩니다.

첫 번째 레이아웃 전환 과정에서 텍셀 데이터를 꼭 보존해야 하는 상황은 그리 많지 않습니다. 대표적인 예로, 이미지를 스테이징 이미지로 쓰면서 ``VK_IMAGE_TILING_LINEAR`` 레이아웃과 조합하여 사용하는 경우가 있습니다. 이 경우에는 이미지에 텍셀 데이터를 먼저 업로드한 뒤, 데이터 손실 없이 전송 소스(transfer source)로 레이아웃을 전환해야 하기 때문입니다. 하지만 우리의 경우, 이미지를 먼저 전송 데스티네이션(transfer destination) 상태로 전환한 다음 버퍼 객체에서 텍셀 데이터를 복사해 올 것이므로 데이터 보존 특성이 필요 없습니다. 따라서 안심하고 ``VK_IMAGE_LAYOUT_UNDEFINED``를 사용하시면 됩니다.

[source,cpp]
----
// void createTextureImage()
imageInfo.usage = VK_IMAGE_USAGE_TRANSFER_DST_BIT | VK_IMAGE_USAGE_SAMPLED_BIT;
----

``usage`` 필드는 버퍼를 생성할 때 보았던 것과 의미가 같습니다. 이 이미지는 버퍼 데이터를 복사해 올 대상(destination)으로 쓰일 것이므로 전송 데스티네이션(``VK_IMAGE_TRANSFER_DST_BIT``)으로 설정해야 합니다. 또한 셰이더에서 이 이미지에 접근해 메시에 색을 입혀야 하므로, usage 설정에 ``VK_IMAGE_USAGE_SAMPLED_BIT``도 반드시 포함해야 합니다.

[source,cpp]
----
// void createTextureImage()
imageInfo.sharingMode = VK_SHARING_MODE_EXCLUSIVE;
----

이 이미지는 오직 하나의 큐 패밀리, 즉 그래픽 작업(및 전송 작업까지 함께)을 지원하는 큐 패밀리에서만 사용됩니다.

[source,cpp]
----
// void createTextureImage()
imageInfo.samples = VK_SAMPLE_COUNT_1_BIT;
imageInfo.flags = 0;
----

``samples`` 플래그는 멀티샘플링(multisampling)과 관련이 있습니다. 이는 어태치먼트(attachment)로 사용될 이미지에만 해당하므로, 여기서는 샘플 수를 1(VK_SAMPLE_COUNT_1_BIT)로 고정합니다. 이미지에는 스파스 이미지(sparse images)와 관련된 몇 가지 선택적 플래그가 더 있습니다. 스파스 이미지는 특정 영역에만 실제로 메모리가 할당되는 이미지입니다. 예를 들어 복셀 지형에 3D 텍스처를 사용하는 경우, 대량의 "공기(빈 공간)" 데이터를 저장하느라 메모리를 낭비하는 일을 방지하기 위해 이 기능을 쓸 수 있습니다. 이번 튜토리얼에서는 사용하지 않으므로 기본값인 ``0``으로 둡니다.

[source,cpp]
----
// void createTextureImage()
if (vkCreateImage(_device, &imageInfo, nullptr, &_textureImage) != VK_SUCCESS) {
    throw std::runtime_error("failed to create image!");
}
----

이미지는 {vkCreateImage}[``vkCreateImage``] 함수를 사용해 생성하며, 특별히 주목할 만한 매개변수는 없습니다. 간혹 그래픽 하드웨어에 따라 ``VK_FORMAT_R8G8B8A8_SRGB`` 포맷을 지원하지 않을 수도 있습니다. 원래는 지원 가능한 대체 포맷 목록을 준비해 두고 그중 가장 좋은 것을 선택하는 과정을 거쳐야 합니다. 하지만 이 포맷은 워낙 널리 지원되기 때문에 여기서는 해당 단계를 건너뛰겠습니다. 다른 포맷을 쓰면 번거로운 데이터 변환 작업도 필요해집니다. 이와 관련된 포맷 선택 시스템은 나중에 link:../DepthBuffering.html[깊이 버퍼(depth buffer) 장]에서 다시 다루며 구현해 볼 예정입니다.

[source,cpp]
----
// void createTextureImage()
VkMemoryRequirements memRequirement;

vkGetImageMemoryRequirements(_device, _textureImage, &memRequirement);

VkMemoryAllocateInfo allocInfo{
    .sType = VK_STRUCTURE_TYPE_MEMORY_ALLOCATE_INFO,
    .allocationSize = memRequirement.size,
    .memoryTypeIndex = findMemoryType(memRequirement.memoryTypeBits, VK_MEMORY_PROPERTY_DEVICE_LOCAL_BIT),
};

if (vkAllocateMemory(_device, &allocInfo, nullptr, &_textureImageMemory) != VK_SUCCESS) {
    throw std::runtime_error("failed to allocate image memory!");
}

vkBindImageMemory(_device, _textureImage, _textureImageMemory, 0);
----

이미지에 메모리를 할당하는 방식은 버퍼 메모리를 할당할 때와 완전히 똑같습니다. {vkGetBufferMemoryRequirements}[``vkGetBufferMemoryRequirements``] 대신 {vkGetImageMemoryRequirements}[``vkGetImageMemoryRequirements``]를 사용하고, {vkBindBufferMemory}[``vkBindBufferMemory``] 대신 {vkBindImageMemory}[``vkBindImageMemory``]를 사용하면 됩니다.

현재 작성 중인 함수의 크기가 이미 꽤 커진 데다가, 향후 다른 장에서도 이미지를 더 만들어야 하므로 버퍼 때와 마찬가지로 이미지 생성 로직을 ``createImage``라는 별도 함수로 추상화하는 것이 좋습니다. 함수를 새로 만들고, 이미지 객체 생성 및 메모리 할당 코드를 그곳으로 옮겨줍니다.

[source,cpp]
----
void createImage(uint32_t width, uint32_t height, VkFormat format, VkImageTiling tiling, VkImageUsageFlags usage,
                 VkMemoryPropertyFlags properties, VkImage& image, VkDeviceMemory& imageMemory) {
    VkExtent3D extent{
        .width = width,
        .height = height,
        .depth = 1,
    };
    VkImageCreateInfo imageInfo{
        .sType = VK_STRUCTURE_TYPE_IMAGE_CREATE_INFO,
        .flags = 0,
        .imageType = VK_IMAGE_TYPE_2D,
        .format = format,
        .extent = extent,
        .mipLevels = 1,
        .arrayLayers = 1,
        .samples = VK_SAMPLE_COUNT_1_BIT,
        .tiling = tiling,
        .usage = usage,
        .sharingMode = VK_SHARING_MODE_EXCLUSIVE,
        .initialLayout = VK_IMAGE_LAYOUT_UNDEFINED,
    };

    if (vkCreateImage(_device, &imageInfo, nullptr, &image) != VK_SUCCESS) {
        throw std::runtime_error("failed to create image!");
    }

    VkMemoryRequirements memRequirement;

    vkGetImageMemoryRequirements(_device, image, &memRequirement);

    VkMemoryAllocateInfo allocInfo{
        .sType = VK_STRUCTURE_TYPE_MEMORY_ALLOCATE_INFO,
        .allocationSize = memRequirement.size,
        .memoryTypeIndex = findMemoryType(memRequirement.memoryTypeBits, VK_MEMORY_PROPERTY_DEVICE_LOCAL_BIT),
    };

    if (vkAllocateMemory(_device, &allocInfo, nullptr, &imageMemory) != VK_SUCCESS) {
        throw std::runtime_error("failed to allocate image memory!");
    }

    vkBindImageMemory(_device, image, imageMemory, 0);
}
----

이 튜토리얼을 진행하면서 앞으로 만들 이미지마다 가로, 세로, 포맷, 타일링 모드, usage, 메모리 속성 등이 모두 달라질 것이므로, 이 값들을 함수의 매개변수로 구성했습니다.

이제 ``createTextureImage`` 함수를 다음과 같이 단순하게 정리할 수 있습니다.

[source,cpp]
----
void createTextureImage() {
    int texWidth, texHeight, texChannels;
    stbi_uc* pixels = stbi_load("./textures/texture.jpg", &texWidth, &texHeight, &texChannels, STBI_rgb_alpha);
    VkDeviceSize imageSize = texWidth * texHeight * 4;

    if (!pixels) {
        throw std::runtime_error("failed to load texture image!");
    }

    VkBuffer stagingBuffer;
    VkDeviceMemory stagingBufferMemory;

    createBuffer(imageSize, VK_BUFFER_USAGE_TRANSFER_SRC_BIT,
                    VK_MEMORY_PROPERTY_HOST_VISIBLE_BIT | VK_MEMORY_PROPERTY_HOST_COHERENT_BIT, stagingBuffer,
                    stagingBufferMemory);

    void* data;
    vkMapMemory(_device, stagingBufferMemory, 0, imageSize, 0, &data);
    memcpy(data, pixels, static_cast<size_t>(imageSize));
    vkUnmapMemory(_device, stagingBufferMemory);

    stbi_image_free(pixels);

    createImage(texWidth, texHeight, VK_FORMAT_R8G8B8A8_SRGB, VK_IMAGE_TILING_OPTIMAL,
                VK_IMAGE_USAGE_TRANSFER_DST_BIT | VK_IMAGE_USAGE_SAMPLED_BIT, VK_MEMORY_PROPERTY_DEVICE_LOCAL_BIT,
                _textureImage, _textureImageMemory);
}

== 레이아웃 전환 (Layout transitions)

이제 작성할 함수도 커맨드 버퍼를 기록(record)하고 실행하는 과정을 거쳐야 합니다. 그러니 이 시점에서 해당 로직을 한두 개의 헬퍼 함수(helper function)로 분리해 두는 것이 좋습니다.

[source,cpp]
----
VkCommandBuffer beginSingleTimeCommands() {
    VkCommandBufferAllocateInfo allocInfo{
        .sType = VK_STRUCTURE_TYPE_COMMAND_BUFFER_ALLOCATE_INFO,
        .commandPool = _commandPool,
        .level = VK_COMMAND_BUFFER_LEVEL_PRIMARY,
        .commandBufferCount = 1,
    };

    VkCommandBuffer commandBuffer;

    vkAllocateCommandBuffers(_device, &allocInfo, &commandBuffer);

    VkCommandBufferBeginInfo beginInfo{
        .sType = VK_STRUCTURE_TYPE_COMMAND_BUFFER_BEGIN_INFO,
        .flags = VK_COMMAND_BUFFER_USAGE_ONE_TIME_SUBMIT_BIT,
    };

    vkBeginCommandBuffer(commandBuffer, &beginInfo);

    return commandBuffer;
}

void endSingleTimeCommands(VkCommandBuffer commandBuffer) {
    vkEndCommandBuffer(commandBuffer);

    VkSubmitInfo submitInfo{
        .sType = VK_STRUCTURE_TYPE_SUBMIT_INFO,
        .commandBufferCount = 1,
        .pCommandBuffers = &commandBuffer,
    };

    vkQueueSubmit(_graphicsQueue, 1, &submitInfo, VK_NULL_HANDLE);
    vkQueueWaitIdle(_graphicsQueue);

    vkFreeCommandBuffers(_device, _commandPool, 1, &commandBuffer);
}
----

이 헬퍼 함수들의 코드는 기존 ``copyBuffer``에 작성했던 코드를 바탕으로 만듭니다. 함수 분리를 마치면 기존의 ``copyBuffer`` 함수를 다음과 같이 아주 간단하게 줄일 수 있습니다.

[source,cpp]
----
void copyBuffer(VkBuffer srcBuffer, VkBuffer dstBuffer, VkDeviceSize size) {
    VkCommandBuffer commandBuffer = beginSingleTimeCommands();

    VkBufferCopy copyRegion{
        .srcOffset = 0,
        .dstOffset = 0,
        .size = size,
    };

    vkCmdCopyBuffer(commandBuffer, srcBuffer, dstBuffer, 1, &copyRegion);

    endSingleTimeCommands(commandBuffer);
}
----

만약 우리가 여전히 버퍼만 사용하고 있었다면, 이제 {vkCmdCopyBufferToImage}[``vkCmdCopyBufferToImage``]를 기록하고 실행하는 함수를 만들어 작업을 끝내면 되었을 것입니다. 하지만 이 명령을 실행하려면 먼저 이미지가 올바른 레이아웃 상태에 있어야 합니다. 레이아웃 전환을 처리할 새로운 함수를 만들어 보겠습니다.

[source,cpp]
----
void transitionImageLayout(VkImage image, VkFormat format, VkImageLayout oldLayout, VkImageLayout newLayout) {
    VkCommandBuffer commandBuffer = beginSingleTimeCommands();

    endSingleTimeCommands(commandBuffer);
}

레이아웃 전환을 수행하는 가장 대표적인 방법 중 하나는 이미지 메모리 장벽(image memory barrier)을 사용하는 것입니다. 이러한 파이프라인 장벽은 일반적으로 버퍼의 쓰기 작업이 완료된 후 읽기 작업을 시작하도록 보장하는 등 리소스 접근을 동기화할 때 쓰입니다. 하지만 이에 더해 이미지 레이아웃을 전환하거나, ``VK_SHARING_MODE_EXCLUSIVE`` 설정을 사용할 때 큐 패밀리(queue family) 간의 소유권을 이전하는 용도로도 사용할 수 있습니다. 참고로 버퍼 리소스에도 이와 동일한 역할을 하는 버퍼 메모리 장벽(buffer memory barrier)이 존재합니다.

[source,cpp]
----
VkImageMemoryBarrier barrier{};
barrier.sType = VK_STRUCTURE_TYPE_IMAGE_MEMORY_BARRIER;
barrier.oldLayout = oldLayout;
barrier.newLayout = newLayout;
----

구조체의 처음 두 필드는 레이아웃 전환 전후의 상태를 지정합니다. 이미지의 기존 내용(데이터)을 유지할 필요가 없다면 ``oldLayout``에 ``VK_IMAGE_LAYOUT_UNDEFINED``를 지정해도 괜찮습니다.

[source,cpp]
----
barrier.srcQueueFamilyIndex = VK_QUEUE_FAMILY_IGNORED;
barrier.dstQueueFamilyIndex = VK_QUEUE_FAMILY_IGNORED;
----

만약 장벽을 사용해 큐 패밀리의 소유권을 이전하려는 경우라면, 이 두 필드에 해당 큐 패밀리들의 인덱스를 넣어주어야 합니다. 소유권 이전을 하지 않을 때는 반드시 ``VK_QUEUE_FAMILY_IGNORED``를 설정해야 합니다(이 값은 기본값이 아니므로 직접 명시해야 함에 주의하세요!).

[source,cpp]
----
barrier.image = image;
barrier.subresourceRange.aspectMask = VK_IMAGE_ASPECT_COLOR_BIT;
barrier.subresourceRange.baseMipLevel = 0;
barrier.subresourceRange.levelCount = 1;
barrier.subresourceRange.baseArrayLayer = 0;
barrier.subresourceRange.layerCount = 1;
----

``image``와 ``subresourceRange`` 필드는 영향을 받을 이미지와 그 이미지의 특정 영역을 지정합니다. 우리가 만든 이미지는 배열 형식이 아니고 밉맵 레벨도 없으므로, 여기서는 단 하나의 레벨과 레이어만 지정해 줍니다.

장벽은 기본적으로 동기화를 목적으로 사용됩니다. 따라서 이 리소스와 관련된 어떤 작업이 장벽 '이전'에 완료되어야 하는지(srcAccessMask), 그리고 어떤 작업이 장벽 '이후'까지 대기해야 하는지(dstAccessMask)를 반드시 지정해야 합니다. 앞서 {vkQueueWaitIdle}[``vkQueueWaitIdle``]을 사용해 수동으로 전반적인 동기화를 맞추었더라도 이 마스크 값들은 여전히 설정해 주어야 합니다. 올바른 마스크 값은 이전(old) 레이아웃과 이후(new) 레이아웃이 무엇이냐에 따라 달라지므로, 우리가 어떤 레이아웃 전환을 사용할지 확정한 뒤에 다시 자세히 알아보겠습니다.

[source,cpp]
----
vkCmdPipelineBarrier(
    commandBuffer,  // 장벽 '이전'에 완료되어야 하는 작업들이 어느 파이프라인 단계(pipeline stage)에서 일어나는지 지정
    0 /* TODO */,   // 장벽 '이후'의 작업들이 어느 파이프라인 단계에서 대기해야 하는지를 지정
    0 /* TODO */,   // 0 또는 VK_DEPENDENCY_BY_REGION_BIT
    0,
    0,
    nullptr,
    0,
    nullptr,
    1,
    &barrier
);
----

모든 종류의 파이프라인 장벽은 동일한 함수(``vkCmdPipelineBarrier``)를 통해 제출됩니다. 커맨드 버퍼 매개변수 바로 다음에 오는 첫 번째 인자는 장벽 '이전'에 완료되어야 하는 작업들이 어느 파이프라인 단계(pipeline stage)에서 일어나는지 지정합니다. 두 번째 인자는 장벽 '이후'의 작업들이 어느 파이프라인 단계에서 대기해야 하는지를 지정합니다. 장벽 전후로 지정할 수 있는 파이프라인 단계는, 장벽 앞뒤로 해당 리소스를 어떻게 사용하는지에 따라 결정됩니다. 허용되는 세부 값들은 Vulkan 명세서의 단계별 link:https://www.khronos.org/registry/vulkan/specs/1.3-extensions/html/chap7.html#synchronization-access-types-supported[사양 테이블]에 나열되어 있습니다. 예를 들어 장벽 이후에 유니폼 버퍼(uniform buffer)를 읽어야 한다면, 접근 마스크에는 ``VK_ACCESS_UNIFORM_READ_BIT``를 지정하고 파이프라인 단계에는 해당 유니폼을 읽는 가장 첫 번째 셰이더 단계인 V``K_PIPELINE_STAGE_FRAGMENT_SHADER_BIT`` 등을 지정해야 합니다. 이러한 용도에 셰이더와 무관한 파이프라인 단계를 지정하는 것은 앞뒤가 맞지 않으며, 접근 유형과 일치하지 않는 파이프라인 단계를 지정하면 유효성 검사 레이어(validation layers)에서 경고를 발생시킵니다.

세 번째 매개변수는 ``0`` 또는 ``VK_DEPENDENCY_BY_REGION_BIT``를 받습니다. 후자를 지정하면 장벽이 리전(region, 영역) 단위 조건으로 작동합니다. 즉, 그래픽스 하드웨어가 리소스 전체의 쓰기가 다 끝나기를 기다리지 않고, 이미 쓰기가 완료된 일부 영역부터 먼저 읽기 시작할 수 있도록 허용하는 설정입니다.

마지막 세 쌍의 매개변수는 Vulkan에서 제공하는 세 가지 유형의 파이프라인 장벽 배열을 참조합니다. 각각 일반 메모리 장벽, 버퍼 메모리 장벽, 그리고 우리가 여기서 사용하는 이미지 메모리 장벽입니다. 참고로 지금은 {VkFormat}[``VkFormat``] 매개변수를 활용하지 않고 있지만, 나중에 link:../DepthBuffering.html[깊이 버퍼(depth buffer) 장]에서 특수한 레이아웃 전환을 처리할 때 이 포맷 값을 유용하게 활용할 예정입니다.

== 버퍼를 이미지로 복사하기 (Copying buffer to image)

다시 ``createTextureImage`` 함수로 돌아가기 전에, 마지막으로 헬퍼 함수 하나를 더 작성해 보겠습니다. 바로 ``copyBufferToImage`` 함수입니다.

[source,cpp]
----
void copyBufferToImage(VkBuffer buffer, VkImage image, uint32_t width, uint32_t height) {
    VkCommandBuffer commandBuffer = beginSingleTimeCommands();

    endSingleTimeCommands(commandBuffer);
}
----

버퍼끼리 복사할 때와 마찬가지로, 이번에도 버퍼의 어떤 영역을 이미지의 어떤 영역으로 복사할지 지정해야 합니다. 이 설정은 {VkBufferImageCopy}[``VkBufferImageCopy``] 구조체를 통해 수행됩니다.

NOTE: ``VkImageSubresourceLayers``는 작성자가 추가함

[source,cpp]
----
VkImageSubresourceLayers resource{
    .aspectMask = VK_IMAGE_ASPECT_COLOR_BIT,
    .mipLevel = 0,
    .baseArrayLayer = 0,
    .layerCount = 1,
};
VkBufferImageCopy region{
    .bufferOffset = 0,
    .bufferRowLength = 0,
    .bufferImageHeight = 0,
    .imageSubresource = resource,
    .imageOffset = {0, 0, 0},
    .imageExtent = {width, height, 1},
};
----

구조체의 필드 대부분은 이름만으로 직관적으로 이해할 수 있습니다. ``bufferOffset``은 버퍼 내에서 픽셀 값이 시작하는 바이트 오프셋을 지정합니다. ``bufferRowLength``와 ``bufferImageHeight`` 필드는 메모리에 픽셀이 어떻게 배치되어 있는지를 나타냅니다. 예를 들어 이미지의 행(row) 사이에 패딩 바이트가 들어가 있는 경우 이를 명시할 수 있습니다. 두 필드 모두 ``0``을 지정하면 우리 사례처럼 데이터가 패딩 없이 촘촘하게 배열(**tightly packed**)되어 있음을 의미합니다. ``imageSubresource``, ``imageOffset``, ``imageExtent`` 필드는 이미지의 어느 구역으로 픽셀을 복사해 넣을지 결정합니다.

버퍼에서 이미지로 복사하는 작업은 {vkCmdCopyBufferToImage}[``vkCmdCopyBufferToImage``] 함수를 사용하여 커맨드 큐에 등록(enqueue)합니다.

[source,cpp]
----
vkCmdCopyBufferToImage(commandBuffer, buffer, image, VK_IMAGE_LAYOUT_TRANSFER_DST_OPTIMAL, 1, &region);
----

네 번째 매개변수는 이미지가 현재 어떤 레이아웃을 사용 중인지 나타냅니다. 여기서는 이미지가 픽셀을 복사해 넣기에 가장 최적화된 레이아웃으로 이미 전환되어 있다고 가정합니다. 지금은 픽셀 덩어리 하나를 이미지 전체에 통째로 복사하고 있지만, 원하신다면 VkBufferImageCopy 구조체 배열을 전달하여 하나의 명령으로 하나의 버퍼에서 이미지의 여러 다른 영역으로 복사하는 작업을 한 번에 처리할 수도 있습니다.

== 텍스처 이미지 준비하기 (Preparing the texture image)

이제 텍스처 이미지 설정을 마무리하는 데 필요한 모든 도구가 준비되었으므로, 다시 ``createTextureImage`` 함수로 돌아가겠습니다. 마지막으로 했던 작업은 텍스처 이미지를 생성하는 것이었습니다. 다음 단계는 스테이징 버퍼의 데이터를 텍스처 이미지로 복사하는 것입니다. 이 과정은 다음의 두 단계로 진행됩니다.

* 텍스처 이미지를 ``VK_IMAGE_LAYOUT_TRANSFER_DST_OPTIMAL`` 레이아웃으로 전환
* 버퍼-이미지 복사 작업(buffer to image copy) 실행

방금 우리가 만들어 둔 헬퍼 함수들을 사용하면 아주 쉽게 구현할 수 있습니다.

[source,cpp]
----
// void createTextureImage()
transitionImageLayout(_textureImage, VK_FORMAT_R8G8B8A8_SRGB, VK_IMAGE_LAYOUT_UNDEFINED,
                      VK_IMAGE_LAYOUT_TRANSFER_DST_OPTIMAL);
copyBufferToImage(stagingBuffer, _textureImage, static_cast<uint32_t>(texWidth),
                  static_cast<uint32_t>(texHeight));
----

처음에 이미지를 생성할 때 ``VK_IMAGE_LAYOUT_UNDEFINED`` 레이아웃으로 설정했으므로, ``_textureImage``를 전환할 때의 이전(old) 레이아웃은 해당 값을 지정해야 합니다. 복사 작업을 수행하기 전에는 기존 이미지 내용이 어떻게 되든 상관없기 때문에 이렇게 설정해도 문제가 없다는 점을 기억해 두세요.

최종적으로 셰이더에서 이 텍스처 이미지의 데이터를 읽어와 샘플링(sampling)을 시작하려면, 셰이더가 접근할 수 있도록 다음과 같이 마지막 레이아웃 전환을 한 번 더 거쳐야 합니다.

[source,cpp]
----
transitionImageLayout(_textureImage, VK_FORMAT_R8G8B8A8_SRGB, VK_IMAGE_LAYOUT_TRANSFER_DST_OPTIMAL,
                      VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL);
----

== 전환 장벽 마스크 (Transition barrier masks)

이 상태에서 유효성 검사 레이어(validation layers)를 켜고 애플리케이션을 실행하면, ``transitionImageLayout`` 함수 내부의 접근 마스크(access masks)와 파이프라인 단계(pipeline stages)가 유효하지 않다는 에러 메시지를 보게 될 것입니다. 우리는 전환할 레이아웃의 종류에 맞춰 이 값들을 적절히 설정해 주어야 합니다.

우리가 처리해야 할 레이아웃 전환은 다음 두 가지입니다.

* Undefined → 전송 데스티네이션(transfer destination): 아무것도 기다릴 필요 없이 곧바로 전송 쓰기(transfer writes) 작업을 수행하면 됩니다.
* 전송 데스티네이션 → 셰이더 읽기(shader reading): 셰이더의 읽기 작업은 전송 쓰기 작업이 끝나기를 기다려야 합니다. 구체적으로는 우리가 텍스처를 실제 사용할 공간인 프래그먼트 셰이더(fragment shader)에서의 읽기 작업을 의미합니다.

이 규칙들은 다음과 같은 접근 마스크와 파이프라인 단계를 사용하여 지정합니다.

[source,cpp]
----
VkPipelineStageFlags sourceStage;
VkPipelineStageFlags destinationStage;

if (oldLayout == VK_IMAGE_LAYOUT_UNDEFINED && newLayout == VK_IMAGE_LAYOUT_TRANSFER_DST_OPTIMAL) {
    barrier.srcAccessMask = 0;
    barrier.dstAccessMask = VK_ACCESS_TRANSFER_WRITE_BIT;
    sourceStage = VK_PIPELINE_STAGE_TOP_OF_PIPE_BIT;
    destinationStage = VK_PIPELINE_STAGE_TRANSFER_BIT;
} else if (oldLayout == VK_IMAGE_LAYOUT_TRANSFER_DST_OPTIMAL
            && newLayout == VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL) {
    barrier.srcAccessMask = VK_ACCESS_TRANSFER_WRITE_BIT;
    barrier.dstAccessMask = VK_ACCESS_SHADER_READ_BIT;
    sourceStage = VK_PIPELINE_STAGE_TRANSFER_BIT;
    destinationStage = VK_PIPELINE_STAGE_FRAGMENT_SHADER_BIT;
} else {
    throw std::runtime_error("unsupported layout transition!");
}

vkCmdPipelineBarrier(commandBuffer, sourceStage, destinationStage, 0, 0, nullptr, 0, nullptr, 1, &barrier);
----

앞서 언급한 표(조건문 코드)에서 볼 수 있듯이, 전송 쓰기 작업은 전송 파이프라인 단계(``VK_PIPELINE_STAGE_TRANSFER_BIT``)에서 일어나야 합니다. 이 쓰기 작업은 이전의 그 어떤 작업도 기다릴 필요가 없으므로, 장벽 이전(pre-barrier) 작업의 접근 마스크는 비워두고(0), 파이프라인 단계는 가장 초기 단계인 ``VK_PIPELINE_STAGE_TOP_OF_PIPE_BIT``를 지정하면 됩니다. 한 가지 알아둘 점은 ``VK_PIPELINE_STAGE_TRANSFER_BIT``가 그래픽스나 컴퓨트 파이프라인 내부의 실제 물리적인 단계가 아니라는 것입니다. 이는 전송 연산이 일어나는 일종의 의사 단계(pseudo-stage)에 가깝습니다. 의사 단계에 대한 자세한 정보와 다른 예시들은 link:https://www.khronos.org/registry/vulkan/specs/1.3-extensions/html/chap7.html#VkPipelineStageFlagBits[공식 문서]를 참고하시기 바랍니다.

이미지는 방금 언급한 전송 단계에서 데이터가 쓰인 후, 이어서 프래그먼트 셰이더에서 읽히게 됩니다. 이것이 우리가 접근 마스크에 셰이더 읽기(``VK_ACCESS_SHADER_READ_BIT``)를 지정하고, 파이프라인 단계에는 프래그먼트 셰이더 단계(``VK_PIPELINE_STAGE_FRAGMENT_SHADER_BIT``)를 지정한 이유입니다.

[quote, Vulak tutorial]
____
The image will be written in the same pipeline stage and subsequently read by the fragment shader, which is why we specify shader reading access in the fragment shader pipeline stage.
____

향후 더 많은 레이아웃 전환이 필요해지면 이 함수의 조건문을 확장해 나가면 됩니다. 이제 애플리케이션을 실행하면 에러 없이 성공적으로 구동될 것입니다. 물론 아직 화면에 보이는 시각적 변화는 없습니다.

한 가지 짚고 넘어갈 점은, 커맨드 버퍼를 제출(submission)할 때 시작 부분에서 호스트 쓰기 접근(``VK_ACCESS_HOST_WRITE_BIT``)에 대한 암묵적인 동기화가 일어난다는 사실입니다. ``transitionImageLayout`` 함수는 단 하나의 명령만 가진 커맨드 버퍼를 실행하므로, 레이아웃 전환 과정에서 호스트 쓰기 의존성(dependency)이 필요하다면 이 암묵적 동기화를 활용해 ``srcAccessMask``를 그냥 ``0``으로 설정해도 무방합니다. 이를 명시적으로 작성할지 여부는 개발자의 선택이지만, 개인적으로는 OpenGL 방식처럼 무대 뒤에서 "숨겨진 채" 일어나는 연산에 의존하는 것을 선호하지 않습니다.

사실 모든 종류의 연산을 지원하는 특수한 이미지 레이아웃인 ``VK_IMAGE_LAYOUT_GENERAL``도 존재합니다. 물론 문제는 이 레이아웃이 그 어떤 연산에서도 최적의 성능을 보장하지 못한다는 점입니다. 하지만 이미지를 입력과 출력 양쪽으로 동시에 사용해야 하거나, 사전 초기화된(**preinitialized**) 레이아웃을 벗어난 직후에 이미지를 읽어야 하는 등의 몇 가지 특수한 상황에서는 이 일반 레이아웃이 필수적으로 사용됩니다.

지금까지 작성한, 커맨드를 제출하는 모든 헬퍼 함수들은 큐가 한가해질 때까지 기다리는 동기식(synchronous) 방식으로 설정되어 있습니다. 하지만 실제 애플리케이션에서는 전체적인 처리량(throughput)을 높이기 위해 이러한 연산들을 하나의 커맨드 버퍼에 모아서 비동기식(asynchronous)으로 실행하는 것이 좋습니다. 특히 ``createTextureImage`` 함수 내부의 레이아웃 전환과 복사 연산이 그렇습니다. 헬퍼 함수들이 커맨드를 기록할 수 있는 ``setupCommandBuffer``를 만들고, 지금까지 기록된 명령들을 한 번에 실행하는 ``flushSetupCommands``를 추가하여 비동기 방식을 직접 실험해 보세요. 이 최적화 작업은 텍스처 매핑이 화면에 올바르게 구동되는 것을 먼저 확인한 후에, 텍스처 리소스가 여전히 잘 설정되는지 검증하면서 진행하는 것이 가장 좋습니다.

== 정리 작업 (Cleanup)

함수의 마지막 부분에서 스테이징 버퍼와 여기에 할당되었던 메모리를 해제하는 코드를 추가하여 ``createTextureImage`` 함수를 마무리합니다.

[source,cpp]
----
vkDestroyBuffer(_device, stagingBuffer, nullptr);
vkFreeMemory(_device, stagingBufferMemory, nullptr);
----

메인 텍스처 이미지는 프로그램이 종료될 때까지 사용되므로, 다음과 같이 정리 함수(cleanup)에 해제 코드를 추가해 줍니다.

[source,cpp]
----
void cleanup() {
    cleanupSwapChain();

    vkDestroyImage(_device, _textureImage, nullptr);
    vkFreeMemory(_device, _textureImageMemory, nullptr);
    ...
}
----

이제 이미지 객체에 텍스처 데이터가 올바르게 채워졌습니다. 하지만 그래픽스 파이프라인에서 이 이미지에 접근하려면 추가적인 작업이 필요합니다. 이 내용은 link:./ImageViewAndSampler.html[다음 장]에서 이어서 다루도록 하겠습니다.
